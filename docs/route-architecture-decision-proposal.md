Status: **proposal for independent review**, 2026-09-23. This document does not replace [the current specification](../spec.md), [runtime policy](../skills/jev-auto-router/references/routing-policy.md), or [ADR 0017](adr/0017-per-call-responses-routing.md).

## Decision in one sentence

Keep **per-call Responses routing** as the target, but do **not** copy the [antoniolg gist](https://gist.github.com/antoniolg/62f82f2a5d191fe074e3f5065501993d) directly. First prove a real Codex A→B→A tool loop through a working authenticated transport. Use the gist's local caller-edge topology as one P0 integration candidate, the current repo's single-pair Jev policy as the decision contract, and TypeSafe's confidence gate as a pattern. If P0 fails, reopen the accepted ADR and trial turn/task-boundary routing; do not silently call it per-call routing.

## Are the gist and Pi Jev Router the same architecture?

**No.** They share Jev classification followed by deterministic application code, but differ at the switching boundary and host integration. The gist intercepts each Codex Responses request and rewrites its `model` and `reasoning.effort` before relaying it through a separately running Codex Router. Pi uses its native `input` extension event to call `pi.setModel` before a new task's generation, then retains the current model for continuation. The gist can switch inside one tool loop; Pi intentionally avoids that. [Gist source](https://gist.github.com/antoniolg/62f82f2a5d191fe074e3f5065501993d/cb55ac3e68abe73cdabbd67b63a158f7abf1a736#file-jev_server-py-L1-L49) · [Pi design](https://github.com/win4r/pi-jev-router/blob/319a04482ab060268afe31ff29d51c77119114cd/docs/design.md#L3-L23)

## What to adopt, and what to leave out

| Source | Adopt into this project | Reason to defer or exclude |
| --- | --- | --- |
| Gist | Test its **topology**: a local Responses endpoint plus an authenticated native caller edge, if the user's Codex transport cannot directly serve all target models. Its distinction between user turns, tool steps and compaction is useful input to P0. | Do not copy its raw-text Jev state, prompt-prefix log, SSE marker rewrite, active floating Jev alias, separate tier/depth answers, Astra-on-error, or automatic external-provider retry. Each conflicts with an existing privacy, pair-validity, stream, version, Astra or provider invariant. [Gist](https://gist.github.com/antoniolg/62f82f2a5d191fe074e3f5065501993d/cb55ac3e68abe73cdabbd67b63a158f7abf1a736) [our policy](../skills/jev-auto-router/references/routing-policy.md) |
| Pi | Copy the **verification ideas**: recheck current model availability immediately before activation; separate proposed route from actual activation; avoid replay after any generated output; distinguish a continuation from genuinely new work. | Do not import its task-affinity, cache-based or price-margin selection into V1 without changing the policy and measuring it. Codex has no demonstrated equivalent of Pi's `input` + `setModel` extension seam. [Pi design](https://github.com/win4r/pi-jev-router/blob/319a04482ab060268afe31ff29d51c77119114cd/docs/design.md) |
| Sol Advisor | Reuse the principle that the parent owns acceptance and that independent review reads the actual diff/tests; keep a bounded, explicit handoff if the product later needs worker routing. | Do not present a fresh worker as a model switch inside the original Codex tool loop. It changes the routing unit and cost accounting. [Roles](https://github.com/DannyMac180/sol-advisor/blob/37b75cad535abdd46531f0227483a8842d045ab8/plugins/sol-advisor/skills/orchestration/references/role-contracts.md) |
| TypeSafe official pattern | Use one typed Choice plus a confidence gate and deterministic dispatch to an **already validated pair**; log low-confidence fallback as such. | The pattern supplies no Codex transport and does not justify adding a second semantic selector or using its example threshold without calibration. [Intent Routing](https://docs.typesafe.ai/patterns/intent-routing) [Confidence Routing](https://docs.typesafe.ai/patterns/confidence-routing) |

## Proposed implementation path and decision gates

| Gate | Work and observable result | Go / stop rule |
| --- | --- | --- |
| **P0a: reach a real model** | In an isolated Codex CLI session, test the current direct custom-provider path and the gist's Codex Router caller-edge path as transport candidates. Record actual request model/effort, response model, auth path, route source and raw SSE fidelity. | Select the smallest transport that can actually reach all required GPT models with the user's intended account, without logging or exporting credentials. A model-picker entry or mocked upstream is insufficient. |
| **P0b: cross-model tool loop** | Run one genuine same-session A→B→A loop with a tool call, stream, cancellation, continuation and compaction. Compare tool IDs and response envelopes before/after switching. | Any critical mismatch stops per-call rollout. Reopen ADR 0017 and test task/turn-boundary routing using App Server; Sol Advisor stays a separate agent-orchestration alternative. |
| **P1: shadow** | Keep the chosen transport, run pinned Jev in shadow on representative tasks; record send eligibility, proposed pair, latency distribution, errors, actual model and usage. | No active routing until transport is faithful and the latency/fallback budget is set from these observations. Our six-case synthetic Jev smoke checks only API connectivity. |
| **P2: paired execution** | Same task IDs, repository snapshots, acceptance checks and declared cache conditions for fixed Sol/medium and active Jev; count all model calls, Jev, verification, failures, correction and takeover. | Report completion and first-pass quality before cost. Only claim savings when quality meets a preregistered non-inferiority bound and usage is complete; otherwise report `UNKNOWN`. [Benchmark contract](sdd/benchmark.md) |

## Questions for the final reviewer

1. Does the per-call product objective justify owning the Codex Router caller-edge dependency if direct transport cannot pass P0, or should V1 deliberately become turn-boundary routing?
2. Is the current allowlisted routing state informative enough to distinguish hard coding calls? Our six synthetic live Jev calls were valid but mostly retained Sol; API validity is not route-quality evidence. [Smoke](../bench/jev-smoke.ts)
3. Can the selected transport prove actual model/effort, native session authorization, tool-loop continuity, and unchanged SSE under cancellation and compaction?
4. Are the fallback baseline, Astra admission, and independent verifier still appropriate once real call/quality data exist?
